# 0.2026267.515 — fix(gh): discriminate verb vs command on Class, not Op — the gh: verb surface was dead

## Summary

Fix the `verb:gh` dispatch so the declarative `gh: {op: ..., repo: ..., number: ...}` check surface actually works out-of-process. Before this change **every** `gh:` check step failed with `gh: exit 2`; only the `charly gh …` CLI (which a human types) ever worked.

Three coupled defects in `candy/plugin-gh/plugin.go`:

1. **Wrong discriminator — the load-bearing one.** `provider.Invoke` switched on `req.GetOp() == sdk.OpRun` to mean "this is the command". But the charly check framework dispatches a plugin **verb** with `ops.OpRun` too (the generic runtime selector — `charly/provider_checkenv.go` `invokeVerbProvider` builds `&Operation{Op: ops.OpRun, …}`); the op selector cannot distinguish command from verb. Every out-of-process `gh:` step was therefore routed into `CliMain` with empty args → `gh: exit 2`. The fix switches on `req.GetClass()` (`"command"` vs default `"verb"`), matching the sibling dual-surface plugins (`candy/plugin-agentteams/plugin.go`, `candy/plugin-agent`). An out-of-tree command never reaches gRPC `Invoke` anyway — charly fork/execs it via `syscall.Exec` (`charly/provider_command_external.go`) — so the `Class=="command"` arm is the compiled-in in-proc placement.

2. **Wrong params envelope.** `runVerb` unmarshalled `params_json` straight into `params.GhInput`, but the framework hands a plugin verb the **full `spec.Op`** envelope with the authored input nested under `plugin_input` — the same shape every sibling out-of-process verb decodes (`candy/plugin-bpf/provider.go`, `candy/plugin-appium/provider.go`). `runVerb` now decodes `spec.Op` → `kit.DecodeInput(op.PluginInput, …)`.

3. **Shared verdict pipeline (R3).** The old verb arm returned a hand-rolled `{status:"pass", result:…}`, so authored `exit_status`/`stdout`/`stderr` matchers on a `gh:` step were never evaluated. `runVerb` now folds its result through `sdk.VerbVerdict` — the one matcher implementation every live verb runs.

**Net command-surface change.** The command arm's normal behavior is unchanged: `Class=="command"`, `Op==OpRun` still decodes `{"args":[…]}` and calls `CliMain`. The one added path is a guard — a `Class=="command"` request with `Op≠OpRun` is now rejected with `gh: unsupported command op …`. Pre-fix such a request fell through the old `GetOp()==OpRun` switch into the **verb** arm (silently mis-dispatched); the guard makes the mis-dispatch explicit. Covered by test case 3 below.

No schema, params, or CLI-flag change; the `charly gh …` command path is otherwise unchanged.
